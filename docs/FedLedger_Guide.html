FedLedger — Complete Guide

Federated Learning with Blockchain Audit Trail
B.E. Computer Science (AI & ML) · Bharat College of Engineering · Mumbai University

Part 1 — What is this project and why does it exist

Imagine three hospitals. Each hospital has patient data and wants to train a machine learning model to detect a disease. The problem: patient data is private. Hospital A cannot send its records to Hospital B or to any central server. That is illegal and unethical.

The traditional solution — collect all data in one place and train one model — does not work here.

Federated Learning solves this. Instead of sharing data, each hospital trains a model on its own data locally. Only the model's learned numbers (called weights) are sent to a central server. The server combines those weights from all three hospitals into one improved global model and sends it back. This cycle repeats for several rounds. The raw patient data never leaves any hospital. Ever.

But a new problem appears: how do you trust the central server? What if the server modifies the weights before combining them? What if it lies about the accuracy? There is no way to verify what the server actually did.

This is what FedLedger adds on top. After every training round, the server writes a permanent, tamper-proof record to a blockchain. This record contains the round number, the accuracy achieved, who participated, and a cryptographic fingerprint (hash) of the model weights. Anyone can look at this record and verify that the server behaved honestly.

The blockchain is the audit trail. Once something is written to it, it cannot be changed or deleted. That is the guarantee.

Part 2 — The complete project workflow in theory

Step 1 — The dataset is split into private pieces

We use the Iris flower dataset — 150 samples with 4 measurements each (petal length, petal width, sepal length, sepal width) and a label (which of 3 flower species it is).

This dataset is split into three equal parts of 50 samples each. Each part is saved to a separate folder: one for OrgA, one for OrgB, one for OrgC. After this split, the three organisations never share their data with each other or with the server. The split is done once before training begins.

Step 2 — The blockchain infrastructure is prepared

Before training starts, we deploy a smart contract to a local simulated Ethereum blockchain (run by a tool called Hardhat). Think of Hardhat as a fake blockchain that behaves exactly like the real Ethereum network but costs nothing and runs on your own computer.

The smart contract is a program that lives on this blockchain. It has one job: accept audit records for each training round and store them permanently. It cannot be edited or deleted. The contract is called FLAuditLog.

After deployment, the contract gets an address on the blockchain (like a postal address). The Python code saves this address so it can find and call the contract later.

Step 3 — A training round begins

The FL server starts and waits. Three nodes (OrgA, OrgB, OrgC) connect to the server. The server sends each node the current global model weights (at the start, these are zeros).

Each node takes those global weights, loads its own private 50-sample dataset, and trains a logistic regression model locally. Training on 50 samples is fast — it takes a fraction of a second. The node now has updated weights that reflect what it learned from its own data.

Step 4 — Weights are sent to the server, not data

Each node sends only its updated weights back to the server. These are just numbers — a matrix of coefficients and a vector of intercepts. They do not contain any raw data. You cannot reconstruct the training data from them (with 50 samples and a simple model, the privacy guarantee is not perfect, but the architectural principle is correct).

Step 5 — FedAvg combines the weights

The server runs the FedAvg algorithm (Federated Averaging). This takes the three sets of weights from the three nodes and combines them into one set of global weights. The combination is a weighted average — each node's contribution is proportional to how many samples it trained on. Since all three have 50 samples, they contribute equally.

The formula is: global_weights = (50/150) × OrgA_weights + (50/150) × OrgB_weights + (50/150) × OrgC_weights

This global model is better than any individual node's model because it has seen patterns from all three datasets without any dataset being shared.

Step 6 — The round is logged to the blockchain

Now the server computes a SHA-256 hash of the global weights. A hash is a fixed-length fingerprint of data. If even one number in the weights changes, the hash changes completely. This is the tamper detection mechanism.

The server calls the smart contract's logRound() function with:

  • Round number
  • Accuracy (as an integer — e.g. 74.3% is stored as 743 because Solidity has no decimal type)
  • List of participating nodes
  • The SHA-256 hash of the weights

The blockchain mines this as a transaction. It now exists permanently. The transaction hash (a unique ID for this blockchain write) is saved alongside the round results.

Step 7 — Global weights are sent back to nodes

The server distributes the new global weights to all three nodes. Each node now starts the next round from this improved starting point. This cycle repeats for however many rounds are configured (default: 10).

Step 8 — Verification

At any point, any participant can verify the server's honesty. The process is:

  1. Take the weights you received (or recompute FedAvg yourself from the node weights you saved)
  2. Compute SHA-256 hash of those weights
  3. Read the hash stored on the blockchain for that round
  4. If they match, the server ran FedAvg honestly and did not modify the weights
  5. If they do not match, the server tampered with the aggregation

This is cryptographic proof, not trust. You do not have to believe the server — you can independently verify it.

Step 1 — Generating the data partitions

File: data/generate_partitions.py

This script loads the Iris dataset from scikit-learn, shuffles it with a fixed random seed so results are reproducible, splits it into three equal stratified parts (50 samples each, each part has roughly equal numbers of all three flower classes), and saves them as NumPy binary files (.npy) into data/node1/, data/node2/, and data/node3/.

It also writes a dataset_meta.json file containing the dataset name, total samples, number of features, and row count per node. The frontend reads this file to display accurate information rather than hardcoded values.

Run once: python data/generate_partitions.py

Step 2 — The smart contract

File: blockchain/contracts/FLAuditLog.sol

Written in Solidity, the language for Ethereum smart contracts. It defines one data structure (a struct called TrainingRound) and stores an array of these structs on the blockchain.

The struct contains: round number, accuracy (integer, ×1000), array of participant names, the model hash (stored as bytes32 — exactly 32 bytes, matching SHA-256 output length), a Unix timestamp, and the Ethereum address of whoever called logRound().

The contract has three public functions: logRound() to write a record, getRound(index) to read one record, and totalRounds() to get the count of records written so far. There are no delete or update functions — the records are permanent.

Step 3 — Deploying the contract

File: blockchain/scripts/deploy.js

Hardhat first starts a simulated Ethereum node on http://127.0.0.1:8545. This deploy script compiles FLAuditLog.sol and deploys it to that local chain. After deployment the contract gets an address (e.g. 0x5FbDB2315678...).

The script writes this address and the path to the compiled contract's ABI (Application Binary Interface — the list of functions the contract exposes) into blockchain/contract_config.json. The Python code reads this file to know where the contract lives.

Step 4 — The FL nodes

File: fl_nodes/node.py

This script uses the Flower framework's NumPyClient class. Flower handles all the networking. You just implement four methods that Flower calls at the right time:

  • get_parameters() — returns the current model weights as a list of NumPy arrays: [coef_, intercept_]
  • set_parameters() — takes a list of NumPy arrays from the server and sets them as the model's current weights
  • fit() — calls set_parameters() first to sync with the global model, then trains the local model on the node's private data with model.fit(), then returns the updated weights and the number of samples trained on
  • evaluate() — tests the global model on the node's local test set and returns accuracy as loss (1 minus accuracy, because Flower expects lower to be better)

The script takes a --node argument (1, 2, or 3) to load the right data partition. Three separate terminals run the same script with different node numbers.

Step 5 — The FL server and FedAvg

Files: fl_server/server.py and fl_server/fedavg.py

server.py defines a custom Flower strategy class called FedLedgerStrategy. The key method is aggregate_fit(), which Flower calls after collecting results from all nodes at the end of each round. This is where all the important work happens:

  1. Extract the weights from each node's result. Flower wraps weights in its own format called Parameters. Convert them back to NumPy arrays using fl.common.parameters_to_ndarrays().
  2. Collect the sample count from each node (fit_res.num_examples).
  3. Call federated_average(weights_list, sample_counts) from fedavg.py. This computes the weighted average: for each layer (coef and intercept separately), compute the sum of (node_weight × node_contribution_fraction).
  4. Call compute_weight_hash(global_weights) which converts the weights to a JSON string and computes SHA-256 of that string. Returns a 64-character hex string.
  5. Call self.blockchain_logger.log_round() which writes the record to the smart contract (explained below). Returns the transaction hash.
  6. Append [round_number, accuracy, tx_hash] to self.round_results and write the whole list to app/round_results.json. This is how the dashboard reads the data.
  7. Convert the global weights back to Flower's Parameters format and return them. Flower will send these to all nodes at the start of the next round.

Step 6 — The blockchain logger

File: fl_server/blockchain_logger.py

This is the Python-to-Ethereum bridge. It uses the web3.py library to connect to the Hardhat node running on port 8545.

On startup it reads contract_config.json to get the contract address and ABI, then creates a contract object — a Python representation of the smart contract that lets you call its functions like regular Python methods.

The log_round() method does five things:

  1. Computes the SHA-256 weight hash
  2. Converts accuracy from a float (e.g. 0.743) to an integer (743) because Solidity has no float type. Multiply by 1000, round, store as integer.
  3. Converts the 64-character hex string hash into 32 raw bytes (bytes.fromhex(weight_hash)) to match the Solidity bytes32 type.
  4. Calls contract.functions.logRound(...).transact({"from": account}) which sends an Ethereum transaction to the blockchain. Hardhat mines it instantly.
  5. Waits for the transaction receipt with w3.eth.wait_for_transaction_receipt(tx_hash) and returns the transaction hash as a hex string.

The verify_round() method reads a stored round from the chain using contract.functions.getRound(index).call() (a read, no transaction, no gas), recomputes the hash from the provided weights, and compares them.

Step 7 — The verify API

File: app/verify_server.py

A minimal HTTP server on port 8088. The dashboard cannot import Python directly, so when a user wants to verify weights they paste them into the dashboard and click verify. The dashboard sends those weights as JSON in a POST request to http://127.0.0.1:8088/verify?round=N. This server receives them, calls BlockchainLogger().verify_round(N, weights), and returns {"match": true} or {"match": false}.

CORS headers are included so the browser does not block the cross-origin request.

Step 8 — The launcher

File: run_fedledger.py

Starts everything in the correct order and with the correct delays between steps:

  1. Start Hardhat node (wait 3 seconds for it to be ready)
  2. Run deploy script (blocking — must finish before Python starts)
  3. Start FL server (wait 2 seconds for it to bind port 8080)
  4. Start OrgA node (0.5 second gap)
  5. Start OrgB node (0.5 second gap)
  6. Start OrgC node (0.5 second gap)
  7. Start verify server on port 8088
  8. Start dashboard server on port 5173
  9. Open http://localhost:5173 in the browser

Each process logs to logs/<name>.log. Ctrl+C terminates everything cleanly.

Step 9 — The data bridge

The server writes to app/round_results.json after every round. The format is a JSON array where each element is a three-item array: [round_number, accuracy_float, tx_hash_string].

Example after 3 rounds: 

[
  [1, 72.3, "0x3d7f2a..."],
  [2, 81.0, "0xa4c19b..."],
  [3, 88.7, "0x6e52f0..."]
]

The dashboard polls this file every 2 seconds. A new entry appearing is how it knows a new round has completed.

Part 4 — The dashboard tabs explained

Tab 1 — Overview

This tab is a static introduction to the project. It is the first thing anyone sees when they open the dashboard and it serves as context before you start training.

It contains:

  • A short explanation of what FedLedger does and why — the privacy problem, the FL solution, and the blockchain audit layer.
  • The technology stack displayed as cards — Python, Flower, Hardhat, and Solidity — each with a one-line description of its role.
  • A "How it works" section showing the four stages: partition data, local training, FedAvg aggregation, blockchain audit.
  • Three key properties of the system: zero raw data bytes sent to the server, SHA-256 hash stored on-chain per round, and append-only records (no delete or update in the contract).
  • A button to jump directly to the Live Training tab.

Why it exists: a viva examiner opens the dashboard and immediately understands what they are looking at without needing a separate explanation. The tab also stays accurate — it reads the actual dataset metadata rather than hardcoding numbers.

Tab 2 — Federation (Live Training)

This is the main interactive tab. It shows the FL process happening in real time with an animated diagram.

The diagram shows:

  • Three node boxes at the top — OrgA (bank icon), OrgB (hospital icon), OrgC (government icon)
  • A central FL Server box in the middle
  • A blockchain box at the bottom
  • Animated arrows connecting them that appear and move based on the current phase

The training process is divided into five phases and the diagram animates through them:

  1. Dispatch — global weights sent from server down to nodes (arrows go down)
  2. Training — each node box pulses while training locally (no arrows — data stays local)
  3. Upload — weight arrows travel upward from nodes to server
  4. Aggregate — the server box glows while FedAvg runs
  5. Commit — a transaction is written to the blockchain box

A scrubber (slider) below the diagram lets you control playback. You can drag it backward to replay an earlier round, or forward to step through rounds one at a time. This is the manual mode. There is also an auto mode that plays through rounds automatically, and a speed control.

The sidebar next to the diagram shows a compact live feed of blockchain blocks as they are committed. Each entry shows the round number, accuracy, the participating nodes, and the first few characters of the weight hash.

Why it exists: this tab makes the abstract FL process visible. Without it, training is just text in a terminal. With it, you can point at exactly what is happening at each moment — which is what an examiner wants to see during a viva.

Tab 3 — Ledger (Audit Log)

This tab shows the complete blockchain audit log in full detail.

The left side shows a table with one row per round:

  • Round number
  • Accuracy percentage
  • Participating nodes
  • Full weight hash (all 64 characters)
  • Transaction hash (the blockchain transaction ID)
  • Timestamp
  • Verification status — whether this round's weights have been verified by the user

The right side shows an accuracy chart — a line graph of global model accuracy across all rounds. This makes it visually obvious that the model is improving as rounds progress. Below the chart are four summary statistics: total rounds, best accuracy, latest accuracy, and number of verified blocks.

Why it exists: this is the audit trail itself. If someone questions whether training happened correctly, this tab shows every single round's record exactly as it exists on the blockchain. The data here comes directly from blockchain reads, not from round_results.json, so it is the ground truth.

Tab 4 — Verify

This tab is for cryptographic verification — proving that the server ran FedAvg honestly.

The process a user follows:

  1. Select a round number to verify
  2. Paste the weight array they saved from their own node (in JSON format — a 2-element array: the coefficient matrix and the intercept vector)
  3. Click "Verify Hash"

What happens behind the scenes: the dashboard sends the weights to the verify server at port 8088. The verify server computes SHA-256 of those weights (using the same method that server.py used during training), then reads the hash stored on the blockchain for that round, and compares them.

If they match, the dashboard shows a green "Verified" result. This means: the weights the server distributed are exactly what FedAvg produced. The server did not modify them.

If they do not match, the dashboard shows a red "Mismatch" result. This means: either the user pasted the wrong weights, or the server tampered with the aggregation.

There is also an "Alter one coefficient" button which deliberately corrupts one weight value. This is a demo tool — clicking it and then verifying produces a mismatch, which shows the examiner how tamper detection works in practice.

The right side of this tab shows a real-time event log — every verification attempt, every round completion, and every connection status change is printed here with a timestamp.

Why it exists: this tab is the academic contribution of the project. FL without verification requires trust in the central server. This tab shows that trust is not required — anyone can verify independently. That is the core claim of the project and this tab demonstrates it live.

Part 5 — How to run the project

One-time setup

# Install Python dependencies
pip install -r requirements.txt

# Install Hardhat (inside blockchain/)
cd blockchain
npm install
cd ..

# Install frontend dependencies and build
cd app/web
npm install
npm run build
cd ../..

# Generate the data partitions (once ever)
python data/generate_partitions.py

Every run

python run_fedledger.py

This single command starts everything. The browser opens automatically to http://localhost:5173. Training begins immediately. Open the Federation tab to watch it live.

Optional flags

python run_fedledger.py --rounds 5          # run only 5 rounds instead of 10
python run_fedledger.py --dataset digits    # use handwritten digits dataset (1797 samples)
python run_fedledger.py --no-ui            # skip opening the browser
python run_fedledger.py --skip-build       # skip rebuilding the frontend

If something goes wrong

Each process writes to a log file. Check these first: 

logs/hardhat.log        ← Ethereum node issues
logs/fl-server.log      ← FL training issues, blockchain write failures
logs/node-1.log         ← OrgA training issues
logs/node-2.log         ← OrgB training issues
logs/node-3.log         ← OrgC training issues
logs/verify-server.log  ← hash verification issues
logs/dashboard.log      ← frontend serving issues

Part 6 — Key concepts to know for the viva

Why does raw data never leave the node?

Because the Flower framework only calls two methods that communicate with the server: get_parameters() and fit(). Neither of these return anything except model weights and a sample count. The raw data arrays (X_train, y_train) are stored as instance variables of the client class and never passed to any method that Flower can access.

What is a weight hash and why does it prove anything?

SHA-256 is a one-way function. Given the same input, it always produces the same 256-bit output. Given a different input (even one number changed by 0.0001), it produces a completely different output. So if you compute SHA-256 of the weights you received and it matches what is on the blockchain, the weights were not modified between the server computing them and you receiving them.

Why use a blockchain instead of just a database?

A database can be edited or deleted by whoever controls it. A blockchain record cannot be changed without changing every block that came after it, which would require redoing more computational work than the entire network has done — computationally infeasible. The blockchain's immutability is what gives the audit trail its value.

What is Hardhat and is this a real blockchain?

Hardhat is a development tool that simulates an Ethereum blockchain locally. It behaves exactly like the real Ethereum network in terms of how smart contracts work, how transactions are mined, and how web3.py communicates with it — but it runs on your computer, costs nothing, and resets when you restart it. For a production system you would deploy the same smart contract to the real Ethereum network or a public testnet. The code would not change.

What is FedAvg and why is it weighted?

Federated Averaging (McMahan et al., 2017) combines local models by averaging their weights, weighted by the number of samples each node trained on. A node that trained on 100 samples should have twice the influence on the global model as a node that trained on 50. In our project all three nodes have 50 samples each, so the weights are equal (1/3 each). If you ran with the --dataset digits flag on an unequal split, the weighting would become meaningful.
